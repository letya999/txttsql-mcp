# Архитектура

```text
MCP stdio (rmcp)
  → handler → диалектный SQL guard → именованный DB adapter
                                   → PostgreSQL/CockroachDB: отдельный PgPool и read-only transaction
                                   → ClickHouse: отдельный HTTP client и серверный read-only профиль
  → query and metadata memory (SQLite, opt-in)
  → ontology Markdown (read-only, opt-in)
  → metadata adapter → OpenMetadata / Airflow REST (opt-in)
```

`config.toml` задаёт именованные источники. Один процесс обслуживает разные базы и независимые пулы. `DatabaseAdapter` и `MetadataAdapter` — точки расширения для новых движков и каталогов при сборке. Динамическая загрузка произвольного кода не нужна для нынешних интеграций и расширила бы границу доверия.

Guard разбирает один SQL statement по диалекту, обходит вложенные запросы, отклоняет записи, table functions, опасные функции и ClickHouse `SETTINGS`, сверяет физические таблицы с allowlist, затем заворачивает AST в внешний `SELECT` с лимитом. БД должна дополнительно отвергать запись от самой роли. Разбор SQL не доказывает семантическую корректность метрики: агент должен читать онтологию и метаданные источника.

`list_tables` читает системный каталог только внутри разрешённых схем; `describe_table` проверяет `schema.table` тем же allowlist, что и SQL guard, и возвращает имена и типы столбцов. Эти внутренние запросы используют адаптер и его серверные ограничения чтения.

Успешные запросы и полученные карточки OpenMetadata/Airflow записываются в локальную SQLite только при включённой памяти. Запросы и карточки имеют независимые теги и заметки. Airflow DAG возвращается вместе с задачами и вычисленными связями `from` → `to`. Семантическая память исходного `txttsql` подключается как read-only каталог Markdown и JSON-графов (`ontology`, `joins`, `lineage`, `mart_deps`, `usage`); содержимое не копируется в этот репозиторий. `explore_graph` возвращает ограниченное соседство узла с типизированными рёбрами.
